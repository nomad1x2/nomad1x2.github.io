    What's interesting here is that the process, '4', was using/opening a file in memory. The memfd key annotates a 'memory file descriptor' which "lets us open memory-only files that are not linked into a directory and are not backed by persistent storage. Such a file is described as an "anonymous file". It behaves like a regular file, and so can be modified, truncated, memory-mapped, and so on. However, unlike a regular file, it lives in RAM and has a volatile backing storage. Once all references to the file are dropped, it is automatically released."

    This is a very common technique that adversaries use while creating malware. Their malware can stay in RAM without having anything hard-written to storage; another obfuscation technique to hide what they're doing.

    With that being said, if we can somehow identify the information within that memfd, then maybe we can find more information on malicious IPs and domains.

    The program header offset we are looking for is highlighted in green (0x0b0870). The reason this is the correct offset is because this is the offset that fits all physical addresses we found with the crash tool:

    0x000c0000 ≤ 0x00d6d000 < 0x07fc0000
    0x000c0000 ≤ 0x00d8c000 < 0x07fc0000
    0x000c0000 ≤ 0x00711000 < 0x07fc0000
    0x000c0000 ≤ 0x00dcd000 < 0x07fc0000
    0x000c0000 ≤ 0x00534000 < 0x07fc0000

    Note: we get 0x07fc0000 by adding together the physical address at offset 0x0b0870 (0x000c0000) and the file size (0x7f40000).

    Now that we have the correct program header where the memfd file is located, we can then calculate the specific file offset for each memfd page we located earlier. That formula is:

    headerOffset + (memfdPhysical - headerPhysical) = fileOffset

    0x000b0870 + (0x00d6d000 - 0x000c0000) = 0x00d5d870
    0x000b0870 + (0x00d8c000 - 0x000c0000) = 0x00d7c870
    0x000b0870 + (0x00711000 - 0x000c0000) = 0x00701870
    0x000b0870 + (0x00dcd000 - 0x000c0000) = 0x00dbd870
    0x000b0870 + (0x00534000 - 0x000c0000) = 0x00524870

    We now have all of the pieces to extract this memfd file, and we can do so by using the dd utility:

    dd:

    Usage: dd if= <FILE> of= <FILE> bs= <BYTES> \ skip= <N> count= <N> seek= <N> conv= <CONVS>

    Where:

    if = our input file (memory.dump).
    of = our output file (memfd.recovered).
    bs = read and write up to BYTES bytes at a time.
    skip = skip N ibs-sized input blocks (our calculated file offsets from above).
    count = copy only N input blocks (page offset size difference, 0x1000 from our proc.Maps dump).
    seek = skip N obs-sized output blocks (page offset sizes).
    conv = converts the file as per the comma separated symbol list ('notrunc' appends copied bytes as stream). 

    nomad@LAPTOP-7SLS1EV9:~$ dd if=memory.dump of=memfd.recovered bs=1 \

    Looking closer at FUN_00101609, it matches the behavior of a base64 decoder. It filters valid characters, maps them through a lookup table, and rebuilds raw bytes in 3-byte chunks. The decoded output and its length are returned to the caller, which lines up with how the main function treats its result.

    The decryption itself happens in FUN_001018fb. This function takes a pointer to the encrypted data, a length, and a 32-bit value pulled from the start of the decoded buffer. That 32-bit value acts as the decryption seed. For each byte, the function updates an internal state by adding the fixed constant 0x722633ad, then XORs the current byte using parts of that state along with a one-byte feedback value from the previous byte. The data is modified in place, which explains why the decrypted buffer is passed straight into the next function without copying.

    The string we recovered earlier has to be a base64 encoded string that contains the key + the payload. When FUN_00101609 decodes it, the first four bytes become a 32-bit seed for FUN_001018fb, and everything after that is encrypted payload data.
